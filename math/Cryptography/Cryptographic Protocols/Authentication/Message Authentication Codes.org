A MAC lets shared-key holders authenticate messages. It targets accepted
forgeries, not message disclosure or impersonation by another key holder.

* Syntax and correctness

For parameterized, efficiently represented spaces \(\mathcal K,\mathcal M,
\mathcal T\), a MAC consists of efficient algorithms

\[
t\leftarrow\mathsf{Tag}(k,m),\qquad
\mathsf{Ver}(k,m,t)\in\{0,1\}.
\]

The key is uniform in \(\mathcal K\). Tagging may be randomized; verification
is deterministic and rejects malformed inputs. For every key and message,

\[
\Pr[\mathsf{Ver}(k,m,\mathsf{Tag}(k,m))=1]=1,
\]

over tagging coins [cite:@fioreCryptographicProtocolosApplicatons sec. 6.2].

Send \((m,t)\); verify the possibly modified received pair. Security must hold
despite adaptively chosen tagging queries; correctness alone does not imply it.

* Why encryption does not replace a MAC

For a one-time pad, replacing \(c=k\oplus m\) by \(c\oplus\Delta\)
changes the decrypted message to \(m\oplus\Delta\), without learning the
key or message. PRF masking and counter mode admit the same modification.

Even perfect confidentiality need not imply integrity. Conversely, sending a
message with its MAC reveals \(m\), so authentication does not imply secrecy
[cite:@fioreCryptographicProtocolosApplicatons sec. 6.1].

* Unique valid tags

A MAC has *unique valid tags* if exactly one \(t\) is accepted for every
\((k,m)\). Deterministic tagging together with verification by recomputation
and equality has this property.

Deterministic tagging alone is insufficient: verification might accept tags
never generated by the tagger. Uniqueness makes fresh-message and strong
unforgeability coincide.

* Limits of authentication

- A previously valid pair can be replayed. A receiver needs an acceptance policy
  and authenticated context, such as sequence numbers, to reject replays.
- Every key holder can create valid tags. Acceptance is evidence relative to
  the set of key holders, not public proof of which one sent the message.
- A MAC is not a digital signature: verification here uses a secret shared key.
- Separate confidentiality and authentication primitives need a justified
  composition; naming both does not itself prove authenticated encryption.

These limits persist despite unforgeability
[cite:@fioreCryptographicProtocolosApplicatons sec. 6.5].
